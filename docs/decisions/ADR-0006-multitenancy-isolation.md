# ADR-0006：共享数据库的纵深多租户隔离

- 状态：Accepted
- 日期：2026-07-16

## 背景

平台从第一版开始要求多租户，Memory 向量召回、Artifact、Worker 和插件工具都可能造成跨租户数据泄露。

## 问题

选择每租户独立数据库还是共享数据库，并确定应用、数据库和对象存储的隔离责任。

## 候选方案

1. 每租户独立部署和数据库。
2. 共享表，仅依赖 API 查询条件。
3. 共享数据库/Schema，所有资源带 `tenant_id`，Repository 强制上下文，PostgreSQL RLS 纵深防御，对象与记忆分区。

## 最终选择

选择方案 3。租户 ID 不可变，跨租户外键受约束；API、Worker、向量查询、Artifact 键和 Event 流均携带租户上下文。迁移 Owner、API 运行角色和最小权限 Worker claimer 使用不同数据库角色；运行角色启用并强制 RLS。

## 选择原因

第一版运维成本可控，同时避免只靠开发者记得加过滤条件。RLS 与应用边界提供两层保护。

## 代价

所有查询、测试和迁移更复杂；超级管理员和后台任务必须显式处理租户上下文；RLS 配置错误仍需安全测试发现。

## 后续影响

Goal B/C 建立 TenantContext、复合索引和 RLS 测试基线；SDK 的 API Key/JWT 映射到租户，禁止客户端自报 tenant_id 获得权限。Worker 只用全局 claimer 租赁队列头，随后切换到租户限定事务处理正文，避免长期持有绕过 RLS 的业务连接。

## 可逆性

中等。可按 `tenant_id` 导出并迁移到独立数据库；反向合并更困难，因此 ID 和导出格式从第一版保持全局稳定。
